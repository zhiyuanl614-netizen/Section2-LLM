## 1. Agent B 实际纠正的4个案例（真实发生的 Agent A 错误/不精确）

### 案例1：B001-PDF-03 / D02（主标签错误）

- **pass1 判断：** `Mentioned_Only_Not_Modeled`（厂内冷却仅作背景提及，未被正式建模）。
- **错误类型：** 构念边界混淆——Agent A 把"该论文未使用冷却专用物理方程"误判为"该依赖关系完全停留在背景叙述层面"，忽略了论文确实在自己的仿真测试用例中用 Eq.(2) 把水电依赖关系实例化为具体的图论约束，只是不含冷却专属的热力学细节。
- **根因：** `Mentioned_Only_Not_Modeled` 与 `Generic_Water_Network_Only` 两个标签的判别边界依赖"是否被正式模型使用"而非"是否含冷却专属物理"，Agent A 在两者间选择时权重放错了判别维度。
- **修正后：** `Generic_Water_Network_Only`。
- **可推广的教训：** D02 的标签手册应在后续版本中更明确地给出"构念落在 formal model 使用与否"这一判别优先级高于"是否有冷却专属方程"的显式判例。

### 案例2：B001-PDF-05 / D05（主标签错误）

- **pass1 判断：** `Single_Timescale_Only`。
- **错误类型：** 构念误触发——论文中的"steady-state"措辞被 Agent A 识别为"该论文考虑过多时间尺度问题但只用了单一时间尺度"，但 Agent B 指出论文的 steady-state 框架其实是地震前/后两个静态快照的比较，根本没有涉及 D05 所问的"水-热-水力缓慢演化 vs 电力系统快速动态"这一构念，属于关键词/语境层面的误触发而非真实的时间尺度判断。
- **根因：** "稳态"（steady-state）一词在不同论文语境中含义差异很大；Agent A 未能区分"控制工程意义上的稳态 vs 瞬态"与"D05 构念要求的跨系统时间尺度差"。
- **修正后：** `Not_Addressed`。
- **可推广的教训：** 这是本批次第2次出现"常见工程术语被误认为匹配某个受控标签构念"的模式（第1次见下文PDF-03 D06的"proactive"案例），说明 D05/D06 这类依赖精确构念匹配的维度，应在 prompt 中补充更多"术语表面匹配但构念不匹配"的反例（negative examples）。

### 案例3：B001-PDF-01 / D10（次要标签遗漏，非主标签错误）

- **pass1 判断：** 主标签 `Validation_Generalizability_Limitation` 正确，但次要标签列表遗漏了 `Missing_Factor_Limitation`。
- **错误类型：** 完整性遗漏——原文明确提到极端天气韧性是当前未建模、留待未来工作的一个具名缺失因素，这应被单独记入 `Missing_Factor_Limitation`，但 Agent A 只记录了笼统的"未来工作"方向。
- **根因：** 多选维度（D10 为 multi-select）在证据包含多个独立局限性陈述时，容易被压缩成单一的泛化标签，遗漏具体的次要标签。
- **修正后：** 次要标签补充为 `['Missing_Factor_Limitation', 'Future_Work_Direction']`。

### 案例4：B001-PDF-04 / D07（证据引用错误，标签未变）

- **pass1 判断：** 主标签 `Critical_Facility_Impact` 正确，但引用的证据是论文中一段关于"医院、消防站"的**叙述性举例段落**，而非论文自己真正操作化的证据。
- **错误类型：** 证据等级误用——Agent A 选择了语义上相关但证据强度较弱的叙述性旁白作为主要引用，而忽略了论文 Eq.(32) 中真正把"为电厂供应冷却水"列为一个具名加权服务类别的操作化证据，后者是更强、更贴近论文自身方法的证据。
- **根因：** 当一段证据既有"读起来很贴合标签"的叙述性段落，又有"真正被论文自己的模型使用"的操作化段落时，Agent A 倾向于选择语言更直白、更像人类写作总结的那一段，而非更技术化但证明力更强的操作化段落。
- **修正后：** 证据/引用改为 Eq.(32) 对应段落，标签不变。
- **可推广的教训：** 这是方法论上最值得警惕的一类错误——**标签恰好蒙对了，但证据选择错误**，如果没有 Agent B 的 Evidence check，这类错误完全不会被机器化的 quote-exact-match 校验发现（因为 pass1 引用的叙述性段落本身也是真实存在于原文中的，quote 本身能通过字符串匹配）。这说明**程序化的引用精确匹配（100%通过率）只能验证"引用的文字是否真实存在"，不能验证"引用的是不是最恰当的证据"**——这正是 `02_评估指标/evaluation_metrics_v1.md` 第2节反复强调的解读边界。

## 2. 流程设计暴露的3类"近似错误"（未导致最终标签错误，但是真实的边界问题）

### 2.1 B001-PDF-03 / D03：受控词表缺口（taxonomy gap）

论文的 Eqs.(1)-(5) 是真实存在的、显式的二元图论依赖状态方程（node-node/node-edge/node-path/geographical dependence），但 schema v1.0 现有的6个 D03 类别（如 `Hydraulic_Pressure_Flow_Equation`、`Energy_Power_Balance_Equation`、`Thermal_Hydraulic_Equation`、`Economic_Cost_Coupling_Equation` 等）均不描述这类纯拓扑依赖关系方程。Agent A/B 最终被迫退回 `No_Explicit_Equation_Qualitative_Only`（置信度降至0.5并显式标注"flagged"）——**这不是该记录的错误，而是 schema 本身覆盖面的缺口**。

**建议：** schema v1.1 增加一个新类别，例如 `Topological_Dependency_Equation`（拓扑依赖状态方程），专门覆盖这类"显式但非物理/非经济，而是图论/网络拓扑形式"的耦合方程。在未冻结 v1.1 前，不应擅自引入未经用户确认的新类别（遵循 `P1_frozen_pipeline_config_v1_LOCKED.md` 第3节的变更规则）。

### 2.2 B001-PDF-03 / D06：MCEER 词汇陷阱（keyword trap，successfully avoided）

论文反复使用"proactive absorptive capacity"（主动吸收能力）一词，表面上与 D06 的"主动预见性控制"构念高度相似，但该词实际来自 MCEER 韧性工程框架，指的是"基础设施规划设计阶段的结构韧性属性"，与 D06 要求的"利用信息层快感知与物理慢动态之间的时间尺度差进行实时主动控制"完全是两回事。Agent A 在 pass1 阶段已正确识别这一区别并给出 `Not_Addressed`，Agent B 在 pass2 复核时专门用 `uncertainty_note` 记录了这一"关键词碰撞风险"，pass2 直接 accept，**未产生修订**，说明该陷阱被成功规避，是流程设计（要求同时输出 uncertainty_note 并强制 Agent B 做 entailment check）发挥作用的正面证据。

**与上文案例2（PDF-05 D05 的"steady-state"误触发）对比：** 同样是常见工程术语的表面匹配陷阱，一次被 Agent A 自己正确规避（本案例），一次被 Agent A 误判、靠 Agent B 纠正（案例2）。两次结果不同，说明这类陷阱的识别**不稳定**，不能认为 Agent A 已经"学会"规避此类陷阱，后续扩大语料规模时应持续监控此类误判率，不能因为本批次多数案例正确就放松警惕。

### 2.3 B001-PDF-04 / D06：本文方法 vs 引用框架的区分（successfully resolved）

论文的 IOR（Infrastructure Operational Resilience）指标是作者自己提出的、测量"扰动后恢复情况"的**反应式**（reactive）指标；而论文讨论部分提到的 UC（Unit Commitment）/GA（遗传算法）调度框架是**另行引用**的现有文献方法，具有主动预见性调度的性质。如果 Agent A/B 把"论文提到了 UC/GA 这种主动调度方法"误当作"本文方法具有主动预见性"，就会把 D06 错判为 `Proactive_Anticipatory_Control`。本次抽取正确地将 D06 判定为 `Reactive_Control_Only`（对应论文自己的 IOR 指标），并把"主动政策制定"这一表述正确归入 D10 的未来工作方向（而非误当作本文已实现的方法）。

**说明：** 这与 §1 的 own_method_vs_cited 讨论相呼应（见 `02_评估指标/evaluation_metrics_v1.md` 关于全部50条记录 `own_method_vs_cited` 均为 `Paper_Own_Method` 的异常发现）。本案例恰恰是"论文自身方法"与"引用的他人方法"需要被严格区分的真实场景，本次区分正确，但该正确性体现在 `mechanism_judgment`/`uncertainty_note` 的叙述中，而不是 `own_method_vs_cited` 枚举值的变化——这进一步印证了该字段在当前5篇语料中从未被压力测试到会触发 `Cited_Other_Work` 分支的边界情况。

## 3. 系统性局限（本轮分析无法弥补，需在后续阶段正视）

1. **证据选择质量无法被程序化规则完全捕获**（见案例4）：quote-exact-match 只能验证引用文字真实存在，不能验证其是否为最强证据。这意味着即使未来扩大到30篇语料、100%通过所有程序化校验，仍不能据此宣称"证据引用质量达到100%"。
2. **常见工程术语的表面匹配陷阱识别不稳定**（见§2.2与案例2的对比）：同一类错误模式（steady-state / proactive）在不同论文中一次被规避、一次未被规避，样本量过小（N=5）无法判断这是运气还是系统性能力，必须在扩大语料规模后重新评估该项错误率是否收敛。
3. **Agent A 与 Agent B 共享执行渠道**：本分析能识别的错误类型，本质上都是"同一底层推理过程在第二次独立审阅同一材料时能够自我发现的不一致"，不能排除两次推理共享的系统性盲点（例如：如果 Agent A/B 对某个英文学术词汇存在共同的误解，两轮推理都会犯同样的错，不会被当前协议捕捉到）。这是 Pilot Gate 要求"D02/D04/D05/D06/D08 由领域专家人工抽查"而不能仅靠 Agent B 自证的根本原因，目前该项仍未落实（见 `01_人工金标准审核/agent_assisted_audit_v1.md` 第4节）。

## 4. 对后续阶段（Step 6 跨文献综合、Step 7 FRDI/图表）的直接影响提示

- 跨文献综合阶段引用 D02/D03/D06 相关结论时，应同时引用本文档 §1、§2 的具体案例作为"该维度存在真实判别难度，结论应保留一定不确定性边界"的依据，不应把50条记录的标签当作无条件真值直接拼合成跨文献共识。
